フロントエンド（`frontend/src/`）の単体テストケースが十分かどうかを分析し、`docs/frontend-unit-test-review.md` にレポートを出力してください。

## 対象スコープ

- 分析対象: `frontend/src/**/*.test.ts`（または `*.test.tsx`）
- 対応する本体コード: テストファイルと同ディレクトリの `.ts` / `.tsx` ファイル（`*.test.*` を除く）
- `$ARGUMENTS` で特定のパスまたは名前が指定された場合はそちらのみを対象にする

> **`$ARGUMENTS` の絞り込みについて**: Step 1〜3 の全手順において、絞り込み指定がある場合は以下のルールを適用する。
> - ディレクトリパス（例: `frontend/src/domain/mqtt`）→ そのディレクトリのみを対象にする
> - ファイルパス（例: `frontend/src/domain/http/types.ts`）→ そのファイルのみを対象にする
> - 関数名（例: `topicMatches`）→ その関数が定義されているファイルのみを対象にし、その関数に絞って分析する

## 分析手順

### Step 1: 本体コードの把握

テストファイルを読む前に、対象ファイルの本体コード（`*.test.*` を除く `.ts` / `.tsx`）を読み、以下を列挙する。この列挙はレポートの「対象関数」テーブルに記載する。

- export されている関数・型・定数の一覧
- 各関数の引数の型・意味・取りうる値の範囲
- 関数内の分岐（if / switch / 三項演算子 / `&&` / `||` / `??`）
- エラーを throw しうる箇所（`throw new Error(...)` / Promise rejection）
- 型ガード関数（`is` 関数）の存在（`as` キャストは TypeScript コンパイラの保証がないため、観点 E の throw 箇所として扱う）

### Step 2: 既存テストの読み取り

テストファイルを読み、以下を把握する。

- `describe` / `it` ブロックの構造とテストしているケース
- `vi.mock` / `vi.fn` / `vi.spyOn` の使い方（何をモックし、何を実際に実行しているか）
- `it.each` によるパラメータ化テストの入力値の範囲
- アサーションの内容（戻り値の中身まで検証しているか、`toBeDefined` だけか）
- `vi.mocked(...).mock.calls` 等による呼び出し引数の検証
- `toHaveBeenCalledWith` / `toHaveBeenCalledOnce` 等のモック呼び出し検証

### Step 3: 以下の観点で不足を検出

以下の観点ごとに、**本体コードを根拠に**不足しているテストケースを検出する。推測・一般論は禁止。必ずコードの具体的なファイル名と行番号を根拠にすること。

観点が対象モジュールに該当しない場合（例: 非同期処理が一切ないモジュールへの時間境界観点）は、「該当なし（理由）」と記載してスキップする。

---

#### 観点 A: 正常系の網羅（Happy Path Coverage）

他の境界テストより先に確認すべき前提。各 export 関数の基本的な正常系が揃っているか。

| チェック項目 | フロントエンドでの例 |
|---|---|
| 最も基本的な入力での成功ケース | 必須フィールドだけ埋めたリクエストで期待レスポンスが返るか |
| 複数バリエーション | GET/POST それぞれで `sendRequest` が正常動作するか |
| 戻り値が存在する関数で戻り値の中身を検証 | `toBeTruthy` だけでなく `toEqual` で中身を確認しているか |

---

#### 観点 B: 入力値の境界（Input Boundary）

対象: 引数の型・値の範囲

| チェック項目 | フロントエンドでの例 |
|---|---|
| 空文字列 `""` vs 空白のみ `" "` | トピック文字列・URL・キー名など |
| 数値: 0・負値・MaxSafeInteger | QoS=0, タイムアウト=0 |
| 配列: 空配列 `[]` vs 要素1個 vs 多数 | コレクションの items, headers, params |
| undefined / null の受け渡し | オプション引数・Wails 応答フィールドが null のとき |
| Optional chaining / Nullish coalescing の伝搬 | `?.` や `??` で `undefined` が下流に伝搬したときの最終戻り値 |

> 型ガード関数（`is*` 関数）の境界は観点 H で集中分析する（この表には記載しない）。

---

#### 観点 C: 状態の境界（State Boundary）

対象: モジュールが内部状態を持つ場合 / localStorage / グローバル状態

| チェック項目 | フロントエンドでの例 |
|---|---|
| 初期状態（空）からの操作 | localStorage が空のときの `loadFromStorage` |
| 既存データ上書き | 同じキーに 2 回 `saveToStorage` |
| 削除後の参照 | `removeFromStorage` 後に `loadFromStorage` |
| localStorage が利用不可能な状態 | `setItem` が `QuotaExceededError` を throw する場合 |

---

#### 観点 D: 組み合わせの境界（Combination Boundary）

対象: 複数フィールドの組み合わせ・オプションフラグ

| チェック項目 | フロントエンドでの例 |
|---|---|
| 必須フィールドが欠落 | `method` なし / `url` なしでリクエスト送信 |
| 相互依存フィールド | `auth.type = "basic"` なのに `username` が空 |
| Enabled フラグの組み合わせ | header/param の `enabled: true` / `enabled: false` の混在 |
| ワイルドカードの組み合わせ | MQTT トピック `+/+/#` のような複合パターン |

---

#### 観点 E: 異常系の境界（Error / Rejection Boundary）

対象: エラーパス・例外・Promise rejection

| チェック項目 | フロントエンドでの例 |
|---|---|
| Wails ハンドラが reject した場合 | `Handler.Connect` が `reject` する → client 側も reject するか |
| 不正なデータで throw する箇所 | 未知の tree item type・未知の HTTP メソッドなど |
| JSON パースエラー | `localStorage` に壊れた JSON が入っている |
| エラーメッセージの内容を検証 | `.rejects.toThrow("Unknown tree item type: unknown")` のように文字列まで確認しているか |

---

#### 観点 F: 非同期・時間の境界（Async / Timing Boundary）

対象: Promise・async/await・タイムアウト

| チェック項目 | フロントエンドでの例 |
|---|---|
| Promise を返す関数が正しく `await` されているか（動作として） | 非同期処理が完了する前にアサートされていないか |
| Wails 関数が遅延 resolve する場合 | （Wails はモックするので実際は該当なし、と記載してよい） |
| 並列 Promise（`Promise.all` 等）の失敗伝搬 | 一部の Promise が reject したときに全体がどう振る舞うか |

> テスト記述ミス（`await` 忘れ・`mockResolvedValue` と `mockReturnValue` の混在）は観点 J で報告する。

---

#### 観点 G: Wails バインディング層の検証（Wails Binding Verification）

対象: `vi.mock("../../../wailsjs/...")` を使うファイル

このプロジェクトではバックエンド呼び出しはすべて Wails バインディング経由。インフラ層クライアント（`infrastructure/*/client.ts`）のテストに特有の観点。

| チェック項目 | フロントエンドでの例 |
|---|---|
| 呼び出し引数の完全な検証 | `toHaveBeenCalledWith(arg1, arg2)` で全引数を確認しているか |
| 呼び出し回数の検証 | 1 回だけ呼ばれるべき箇所に `toHaveBeenCalledOnce()` があるか |
| マッピング関数（Wails型 → ドメイン型）の全フィールド確認 | `toEqual` で全フィールドを検証しているか、一部フィールドのみか |
| モックで隠れた動作を明記 | インフラ内部ロジックはモックで隠れるため「モックで未検証」と記載 |

> モックのリセット漏れ・テスト間汚染は観点 J で報告する。

---

#### 観点 H: 型ガード・バリデーション関数の境界（Type Guard Boundary）

対象: `is*` 関数や型アサーション関数（`domain/*/types.ts` など）

このプロジェクトでは `isHttpMethod`・`isBodyType`・`isAuthType` などの型ガード関数が多数存在する。

| チェック項目 | フロントエンドでの例 |
|---|---|
| 全ての有効値で `true` を返すか | `it.each(HTTP_METHODS)(...)` のように定数配列を直接使っているか |
| 無効値で `false` を返すか | 空文字・大文字小文字違い・似た名前の未定義値 |
| 部分一致で `false` を返すか | `"GE"`, `"POSTX"` のような前後一致しない値 |
| 新しい値が定数配列に追加されたときにテストも追従できる構造か | ハードコードされた値でなく定数配列から生成しているか |

---

#### 観点 I: 戻り値・副作用の検証（Return Value / Side Effect）

対象: テストがアサーションで「何を」確認しているか

| チェック項目 | フロントエンドでの例 |
|---|---|
| 戻り値の中身が未検証 | `expect(result).toBeDefined()` のみで `result.statusCode` などを確認していない |
| マッピング結果の全フィールドを確認していない | `toMatchObject` で一部フィールドのみ検証し、他フィールドが化けていても気づけない |
| 副作用（localStorage への書き込み）の確認漏れ | `saveToStorage` 後に実際に `localStorage.getItem` で確認しているか |
| エラー時の戻り値の型・内容を確認 | `rejects.toThrow` でメッセージ文字列まで確認しているか |

---

#### 観点 J: テスト構造の整合性（Test Structure Integrity）

対象: テストコード自体の正しさ・独立性

バックエンド版の観点 J に相当。テストが「実際に動作を検証しているか」に関わる記述ミスを報告する。

| チェック項目 | フロントエンドでの例 |
|---|---|
| `await` 忘れによるフォールスポジティブ | `expect(asyncFn())` を `await` せずにアサートしている（常に pass してしまう） |
| `mockResolvedValue` と `mockReturnValue` の混在 | Promise を返す Wails 関数に `mockReturnValue` を使っているため reject が検出できない |
| `vi.clearAllMocks()` が `beforeEach` にない | 前テストのモック状態が次テストに汚染される |
| `localStorage` のリセット漏れ | `beforeEach` で `localStorage.clear()` されていないため前テストのデータが残る |
| モジュールレベル変数のテスト間汚染 | テストファイルのトップレベルで宣言した変数を `beforeEach` でリセットしていない |

## 制約事項

- **コードを読まずに記載禁止**: 「一般的にこういうケースが必要」という一般論でなく、実際のコードの分岐・型・条件を根拠にすること
- **存在しない分岐を「不足」と報告しない**: 本体コードにその分岐がない場合はテスト不要
- **該当しない観点はスキップ**: 非同期処理がないモジュールへの観点 F など、対象モジュールに関係しない観点は「該当なし（理由）」と記載して省略する
- **モックで隠れた部分を明記**: Wails バインディングをモックしているため検証できない動作は「モックで未検証」と記載（観点 G で報告）
- **テスト構造の問題は観点 J で報告**: `await` 忘れ・`vi.clearAllMocks()` の欠如・テスト間汚染など、テストの正しさに影響する記述ミスは観点 J にまとめる（観点 F・G では動作・バインディングの検証に集中する）
- **型ガード関数は観点 H で集中分析**: `is*` 関数は境界値が多いため、観点 B と重複しても観点 H に詳細を記載する
