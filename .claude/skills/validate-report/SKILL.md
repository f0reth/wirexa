`plan-app` スキルが `docs/` に出力した変更計画書を検証してください。

## 対象ファイルの決定

- `$ARGUMENTS` にファイル名が指定された場合 → そのファイルのみ対象
  - 例: `2026-05-17-add-mqtt-reconnect.md` → `docs/2026-05-17-add-mqtt-reconnect.md`
- `$ARGUMENTS` が空の場合 → `docs/` 配下の全 `.md` ファイルを対象とする

## 実行手順

### Step 1: 計画書の読み込み

対象ファイルを読み込み、以下を把握してください。

- 変更・追加・削除するファイルの一覧と層の分類
- 変更理由・背景（概要セクション）
- 実装方針の内容
- 副作用・注意事項として記述されている内容
- Git 運用の方針（ブランチ名・コミット分割）

### Step 2: 参照先コードの実読

**推測・記憶・想像による判断は禁止。** 計画書が言及しているファイルを必ず開いて確認してください。

- 参照ファイルが実際に存在するか
- 計画書が主張する変更内容（変更理由・現状のコード）が実際のコードと一致するか
- 変更対象ファイル表にある 2〜3 件をランダムに選んで実際にコードを読む

## 5つの観点で評価

### 観点 1: 事実確認（Fact-Check）

- 計画書が参照している **ファイルパス** が実際に存在するか
- 変更理由として挙げられた内容が**コードに実在するか**（存在しない問題を根拠にしていないか）
- 変更対象ファイル表の変更種別（変更/追加/削除）と実際のコードの状態が一致しているか

### 観点 2: 網羅性確認（Completeness-Check）

- 変更が必要なファイルが計画書から**漏れていないか**
- 各層（Domain / Application / Infrastructure / Adapters / フロントエンド各層）への影響が適切に記述されているか
- 副作用・注意事項として記述すべき影響範囲が漏れていないか

**生成物・テストの漏れ（頻出）:**

- バインド対象の Go 構造体・ハンドラメソッドを変更するのに `task wails:generate` が手順に無い
- イベント名を追加するのに `task go:generate:events` と `tools/gen-events/main.go` への追記が手順に無い
- バインド API の振る舞いを変えるのに `frontend/e2e/fake-backend/` の追従が変更対象ファイル表に無い
- 生成物（`frontend/wailsjs/`・`frontend/src/shared/wails-events.ts`）を**手で編集する**計画になっていないか

### 観点 3: 品質・構成確認（Quality-Check）

- 計画書が `plan-app` スキルの出力形式（概要・変更対象ファイル表・実装方針・コード生成・テスト方針・副作用・Git運用）を満たしているか
- 実装方針が**実現可能で具体的**か（「リファクタリングすべき」のような根拠のない抽象的な記述でないか）
- Git 運用として `task format` → `task lint` → `task test` の確認後に main へマージという手順が含まれているか

### 観点 4: プロジェクトアーキテクチャ整合性（Consistency-Check）

このプロジェクトのクリーンアーキテクチャ制約と照合してください。

**バックエンド層構成と実際のパス:**

| 層 | パス | 役割 |
|---|---|---|
| Domain | `internal/domain/` | ビジネスルール・型定義・インターフェース（外部依存なし） |
| Application | `internal/application/` | ユースケース・Service層（`*_service.go`） |
| Infrastructure | `internal/infrastructure/` | MQTT・HTTP・UDP・JSONファイルストレージの実装 |
| Adapters | `internal/adapters/` | Wails RPC ハンドラ（`*_handler.go`）。ドメイン型を直接送受信する薄いパススルー |

**依存方向（厳守・コンパイル時の import 方向）:**

```
adapters ──────┐
application ───┼──→ domain（出力ポートを定義）
infrastructure ┘
```

- `domain` は他のどの層にも依存してはならない。
- `application` / `infrastructure` は `domain` の出力ポートを実装する（依存性逆転）。
- `adapters` は自分で定義したインターフェース（ユースケースの入力ポート）経由でユースケースを呼び出し、`application` を直接 import しない。`application` のサービスはこれを構造的に満たし、その検証は `app.go` で行う。
- 具体型の組み立て・注入は合成ルート `app.go` でのみ行う。

**フロントエンド:** `frontend/src/` も同様のクリーンアーキテクチャ（`domain` / `application` / `infrastructure` / `presentation` / `shared`）を採用。
`wailsjs/` を import してよいのは `infrastructure/` のみ。コンポーネントからの `infrastructure/` 直接 import は禁止（ポート経由で注入する）。

確認項目:
- 提案する変更がこの依存方向を破っていないか（内側の層が外側を import していないか）
- ドメイン型と同型の RPC 用 DTO を `internal/adapters/` に新設していないか（ハンドラはドメイン型の薄いパススルー）
  - この禁止は adapters の RPC DTO に限る。infrastructure の永続化 DTO（`storedXxx`）は必要なもので、どの階層でも domain 型を埋め込んでいないかを確認する
  - 保存対象のフィールドを domain 型に足す場合、stored DTO と変換関数にも足しているか
  - ドメインに対応物の無いアダプタ固有の入力型（例: `log_handler.go` の `LogEntry`）は違反ではない
  - 名前付き文字列型を `string` で受けて内部変換するのは Wails の制約による既定の回避策であり、違反ではない
- 提案内容が既存の設計思想を壊すものになっていないか
- 提案内容が**動作中の機能を破壊・劣化**させるリスクがないか

### 観点 5: バグリスク確認（Bug-Risk-Check）

計画書が提案する変更を適用した場合に新たなバグが発生しないかを確認してください。

| チェック項目 | 確認内容 |
|---|---|
| 副作用の有無 | 呼び出し元・依存モジュール・共有状態に意図しない影響を与えないか |
| エッジケースの未考慮 | 空値・nil・ゼロ値・境界値・エラー時のケースを考慮しているか |
| 型・インターフェース整合性 | 変更後も呼び出し元が期待する型・シグネチャ・インターフェースと一致しているか |
| 並行安全性 | Go コードの場合、変更によって競合状態やデッドロックが生じる可能性はないか |
| 既存テストへの影響 | 変更後に `internal/` 配下の既存テストが壊れる可能性はないか |

## 出力形式

標準出力（チャット上）に以下の構成で出力してください（ファイル出力は不要）。

```
## 検証結果: <対象ファイル名>

### 観点1: 事実確認
- [OK/NG] <確認項目>: <根拠（実際に確認したファイルとコード）>
...

### 観点2: 網羅性
- 漏れあり: <漏れている変更・影響先とその根拠>（なければ「漏れなし」）

### 観点3: 品質・構成
- [OK/NG] <確認項目>: <コメント>
...

### 観点4: アーキテクチャ整合性
- [OK/NG] <確認項目>: <コメント>
...

### 観点5: バグリスク
- [OK/NG] <確認項目>: <根拠または懸念点>
...

### 総合評価
**信頼度**: 高 / 中 / 低
**主な問題**: <NGがあった場合の要約>
**推奨アクション**: <そのまま実装可 / 計画書の修正が必要 / plan-app を再実行すべき>
```

複数ファイルが対象の場合は、ファイルごとに上記セクションを繰り返してください。
