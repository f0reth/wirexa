バックエンド（`internal/`）の単体テストケースが十分かどうかを分析し、`docs/backend-unit-test-review.md` にレポートを出力してください。

---

## プロジェクト固有情報

### 層構成と実際のパス

| 層             | パス                       | 役割                                                         |
| -------------- | -------------------------- | ------------------------------------------------------------ |
| Domain         | `internal/domain/`         | ビジネスルール・型定義（外部依存なし）                       |
| Application    | `internal/application/`    | ユースケース・Service層（http / mqtt / udp）                 |
| Infrastructure | `internal/infrastructure/` | HTTP・MQTT・UDP・JSONストレージの実装                        |
| Adapters       | `internal/adapters/`       | Wails連携・DTO・Handler（現在テストファイルなし）            |
| TestUtil       | `internal/testutil/`       | テスト補助（NoopLoggerなど。テスト対象ではない）             |
| Integration    | `internal/integration/`    | 統合テスト（**単体テスト分析からは除外**。参考程度に確認可） |

**依存方向（厳守）:** `adapters → application → domain ← infrastructure`

### 使用ライブラリ（モック関連）

- テストフレームワーク: `testify` (`require` / `assert` / `mock`)
- モック検証: `mock.AssertExpectations(t)` が標準的な呼び出し確認手段

---

## 対象スコープ

- **分析対象**: `internal/**/*_test.go`（ただし `internal/integration/` を除外）
- **対応する本体コード**: テストファイルと同パッケージの `.go` ファイル
- **`$ARGUMENTS` による絞り込み**: 指定がある場合は Step 1〜3 すべてでその範囲のみを対象にする

| 指定形式       | 例                                             | 動作                                                             |
| -------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| パッケージパス | `internal/application/http`                    | そのパッケージのみ対象                                           |
| ファイルパス   | `internal/application/http/request_service.go` | そのファイルのみ対象                                             |
| 関数名         | `SendRequest`                                  | その関数が定義されているファイルのみ対象し、その関数に絞って分析 |

---

## 分析手順

### Step 1: 本体コードの把握

テストファイルを読む前に、対象パッケージの本体コード（`_test.go` を除く `.go` ファイル）を読み、以下を列挙してください。この列挙はレポートの「対象関数」テーブルに記載します。

- テスト対象の関数・メソッド一覧（公開・非公開両方）
- 各関数の入出力の型と意味
- 関数内の分岐（if/switch/for）と状態遷移
- エラーを返しうる箇所

### Step 2: 既存テストの読み取り

テストファイルを読み、以下を把握してください。

- テスト関数名と実際にテストしているケース
- モックの使い方（何をモックし、何を実際に実行しているか）
- テーブルドリブンテストの入力値の範囲
- アサーションの内容（戻り値の中身まで検証しているか、エラー有無だけか）
- モック検証（`AssertExpectations` 等が呼ばれているか）

### Step 3: 不足ケースの検出

以下の観点ごとに、**本体コードを根拠に**不足しているテストケースを検出してください。推測・一般論は禁止。必ずコードの具体的なファイル名と行番号を根拠にすること。

観点が対象パッケージに該当しない場合（例: 並行処理が一切ないパッケージへの観点 G）は、「該当なし（理由）」と記載してスキップしてください。

---

#### 観点 A: 正常系の網羅（Happy Path Coverage）

他の境界テストより先に確認すべき前提。各関数の基本的な正常系が揃っているか。

| チェック項目                               | 例                                                             |
| ------------------------------------------ | -------------------------------------------------------------- |
| 最も基本的な入力での成功ケース             | 必須フィールドだけ埋めたリクエストで正常レスポンスが得られるか |
| 複数の正常バリエーション                   | GET/POST/PUTそれぞれに正常系があるか                           |
| 戻り値が存在する関数で成功時の戻り値を検証 | `err == nil` だけでなく戻り値の中身まで確認しているか          |

---

#### 観点 B: 入力値の境界（Input Boundary）

対象: 数値・文字列・スライス・マップ等の引数

| チェック項目                                 | 例                          |
| -------------------------------------------- | --------------------------- |
| 最小値・最大値（0, 1, -1, MaxInt, MinInt等） | len=0, len=1                |
| 空文字列 vs 空白のみ vs nil                  | `""`, `" "`, `nil`          |
| Unicode・特殊文字（\n, \t, null byte）       |                             |
| 許容外の値（バリデーション境界の前後）       | 許可メソッド一覧の直前/直後 |

---

#### 観点 C: 状態遷移の境界（State Transition Boundary）

対象: オブジェクトの状態機械・フラグ・ライフサイクル

| チェック項目                         | 例                                    |
| ------------------------------------ | ------------------------------------- |
| 初期状態からの操作                   | 未初期化のサービスへの呼び出し        |
| 終了状態からの操作（二重クローズ等） | Close後にSendRequest                  |
| 許可されていない状態遷移             | 接続前にPublish                       |
| 状態をまたいだ操作の順序依存         | Create→Update→Delete の中間をスキップ |

---

#### 観点 D: 組み合わせの境界（Combination Boundary）

対象: 複数フィールドの組み合わせ・オプション

| チェック項目                           | 例                               |
| -------------------------------------- | -------------------------------- |
| 必須フィールドが欠落した場合           | URL指定なし、Method指定なし      |
| 相互排他フィールドの同時指定           | BasicAuthとBearerTokenを両方指定 |
| 依存関係のあるフィールド               | BodyあるのにContent-Typeなし     |
| Enabled=true/falseのフラグの組み合わせ | HeaderのEnabled制御              |

---

#### 観点 E: 異常系の境界（Error Boundary）

対象: エラーパス・リカバリ・エラー伝搬

| チェック項目                           | 例                               |
| -------------------------------------- | -------------------------------- |
| 依存コンポーネントのエラー返却         | Transportがerrを返す             |
| エラーの種類による分岐（errors.Is/As） | sentinel errorの判定             |
| エラー後の状態整合性                   | エラー後にリソースリークがないか |
| パニックになりうる箇所                 | nilポインタデリファレンス        |

---

#### 観点 F: 時間の境界（Time Boundary）

対象: タイムアウト・タイマー・コンテキストキャンセル

| チェック項目                       | 例                                       |
| ---------------------------------- | ---------------------------------------- |
| contextがキャンセル済みで渡される  | `ctx, cancel; cancel(); svc.Do(ctx,...)` |
| タイムアウト直前・直後             | 100ms制限に99ms vs 101ms                 |
| ゼロ値のタイムアウト               | `Timeout: 0`                             |
| 即時キャンセル（デッドライン過去） | `DeadlineExceeded` context               |

---

#### 観点 G: 並行性の境界（Concurrency Boundary）

対象: goroutine・mutex・チャネル・共有状態

| チェック項目                 | 例                                    |
| ---------------------------- | ------------------------------------- |
| 同一リソースへの並行書き込み | 複数goroutineから同じサービス呼び出し |
| goroutineリーク              | 長時間ブロッキング後のキャンセル      |
| 競合状態（race detector）    | `go test -race` で落ちるパターン      |
| チャネルのclose後のsend      |                                       |

---

#### 観点 H: 環境の境界（Environment Boundary）

対象: ファイルシステム・ネットワーク・外部依存

| チェック項目                   | 例                     |
| ------------------------------ | ---------------------- |
| ストレージファイルが存在しない | 初回起動時の空状態     |
| ストレージが破損（不正JSON）   | `{invalid json}`       |
| ストレージが読み取り専用       |                        |
| ネットワーク不達               | 到達不能ホストへの接続 |

---

#### 観点 I: 戻り値・副作用の検証（Return Value / Side Effect）

対象: テストがアサーションで「何を」確認しているか

| チェック項目                                               | 例                                                                               |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 戻り値の中身が未検証                                       | `err == nil` のみ確認し `Response.StatusCode` 等が未確認                         |
| 副作用（DB書き込み・ファイル生成・イベント発火）の確認漏れ | Createが成功した後、実際にデータが保存されたか確認していない                     |
| エラー時の戻り値の確認漏れ                                 | エラーが返ることは確認しているが、エラーの内容（メッセージ・型）を検証していない |

---

#### 観点 J: モックの検証（Mock Assertion Coverage）

対象: testify/mock のモックが正しく呼ばれたかの確認

| チェック項目                       | 例                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------ |
| `AssertExpectations(t)` 未呼び出し | モックを設定しているが最後に呼ばれたか検証していない                     |
| 呼び出し引数の未検証               | `On("Method", mock.Anything)` だけで実際の引数値を確認していない         |
| 呼び出し回数の未検証               | 1回だけ呼ばれるべきメソッドが複数回呼ばれてもパスするテスト              |
| モックで隠れた動作の明記           | インフラ層をモックしているため検証できない動作は「モックで未検証」と記載 |

---

## 制約事項

- **コードを読まずに記載禁止**: 「一般的にこういうケースが必要」という一般論でなく、実際のコードの分岐・型・条件を根拠にすること
- **存在しないケースを「不足」と報告しない**: 本体コードにその分岐がない場合はテスト不要
- **該当しない観点はスキップ**: 並行処理がないパッケージへの観点 G など、対象パッケージに関係しない観点は「該当なし（理由）」と記載して省略する
- **モックで隠れた部分を明記**: インフラ層をモックしているため検証できない動作は「モックで未検証」と記載（観点 J で報告）
- **`go test -race` 観点を忘れない**: 並行処理があるパッケージは観点 G を必ずチェック
- **`internal/adapters/` はテストなし**: 現時点でテストファイルが存在しないため、対象外（`$ARGUMENTS` で明示指定された場合のみ「テストなし」として記録する）
