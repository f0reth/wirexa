## このスキルの概要

- **出力先**: `docs/bug-investigation.md`（ディレクトリがなければ作成する）
- **後続処理**: このスキルが生成したレポートは `validate-report` スキルで再検証される
- **ツール**: Read・Grep・Glob を使ってコードを読む。記憶や推測によるコード判断は禁止

このプロジェクト全体（または `$ARGUMENTS` で指定された範囲）に存在する潜在的なバグを調査し、`docs/bug-investigation.md` にレポートを出力してください。

---

## 調査スコープ

### デフォルト（`$ARGUMENTS` なし）: プロジェクト全体

| レイヤー | 対象 |
|----------|------|
| Go バックエンド | `internal/` 配下の `.go` ファイル（`_test.go` は参考として読むが主対象外） |
| フロントエンド | `frontend/src/` 配下の `.ts` / `.tsx` ファイル（`.test.ts` は参考） |
| 除外 | `wailsjs/` 配下の自動生成バインディング（手動変更不要のため） |

主要機能: **MQTT クライアント**・**HTTP クライアント**・**UDP 送受信**

### `$ARGUMENTS` による絞り込み

`$ARGUMENTS` でパス・パッケージ・関数名が指定された場合はそこに絞る。

| 指定形式 | 例 | 対象範囲 |
|----------|-----|---------|
| パッケージパス | `internal/application/mqtt` | そのパッケージのみ |
| ファイルパス | `frontend/src/application/http/request.ts` | そのファイルのみ |
| 関数名 | `PublishMessage` | その関数が定義されているファイルのみ |

## 調査の前提

**推測・一般論・記憶によるコード判断は禁止。必ず実際のファイルを読んで確認すること。**

調査前に以下を把握する：

1. `CLAUDE.md` でアーキテクチャを確認する
2. `internal/domain/` と `frontend/src/domain/` を Read して型・インターフェースを把握する
3. 対象スコープの実装ファイルを Read する

## 調査観点

### 【Go バックエンド】

#### 観点 G1: nil ポインタ・ゼロ値アクセス

| チェック項目 | 確認すること |
|---|---|
| インターフェースの nil チェック漏れ | 依存注入されたフィールドを使う前に nil かどうか確認しているか |
| マップの未初期化アクセス | `var m map[string]T` のまま `m[key]` や `m[key] = v` していないか |
| スライスの未初期化アクセス | nil スライスへの範囲外アクセス |
| ポインタ型フィールドのデリファレンス | optional なポインタフィールドをチェックせず `*p` していないか |

#### 観点 G2: エラーハンドリングの欠陥

| チェック項目 | 確認すること |
|---|---|
| エラーの握りつぶし | `_` でエラーを破棄していないか（正当な理由なく） |
| エラー後の処理継続 | `if err != nil` でリターンせず後続処理が走るパスがないか |
| `errors.Is` / `errors.As` の欠如 | sentinel error や wrapped error を `==` で比較していないか |
| `fmt.Errorf` のラップ忘れ | `%w` の代わりに `%s` / `%v` を使ってコンテキストが失われていないか |

#### 観点 G3: 並行安全性（Goroutine / Mutex）

| チェック項目 | 確認すること |
|---|---|
| 共有状態へのロックなしアクセス | `sync.Mutex` や `sync.RWMutex` を使うべき箇所でロックしていないか |
| `defer mu.Unlock()` の正しい配置 | ロック後の早期リターン前に Unlock を忘れていないか |
| goroutine リーク | 起動した goroutine がキャンセル・終了可能になっているか（context 連携） |
| チャネルの二重クローズ | `close(ch)` を複数箇所から呼ぶ可能性がないか |
| `sync.WaitGroup` の誤用 | `Add` と `Done` の呼び出し数が一致しているか |
| `sync.Once` の誤用 | `Do` に渡した関数がパニックした場合、以降の呼び出しはスキップされる（リトライできない）ことを考慮しているか |

#### 観点 G4: リソースリーク

| チェック項目 | 確認すること |
|---|---|
| `defer` による Close 漏れ | `os.File`, `net.Conn`, `io.ReadCloser` 等を開いたら必ず Close しているか |
| HTTP レスポンスボディの Close 漏れ | `resp.Body.Close()` が defer されているか（エラー時も含む） |
| context のキャンセル漏れ | `context.WithCancel` / `WithTimeout` で作成した context を使い終わったら cancel しているか |
| `time.Ticker` の Stop 漏れ | `time.NewTicker` を使ったら `defer ticker.Stop()` しているか |
| UDP ソケットの Close 漏れ | `net.UDPConn` を開いたら必ず Close しているか（UDP 機能固有） |

#### 観点 G5: 型変換・データ変換の欠陥

| チェック項目 | 確認すること |
|---|---|
| 整数オーバーフロー | `int` ↔ `int32` ↔ `int64` の変換で値域を超えるケースがないか |
| JSON デコード後の型アサーション | `interface{}` を型アサーションする際にカンマ ok イディオムを使っているか |
| 文字列 ↔ バイト列変換 | 変換後に内容が意図通りかを確認しているか |

#### 観点 G6: ロジックバグ・境界条件

| チェック項目 | 確認すること |
|---|---|
| off-by-one エラー | スライスのインデックス境界、ループの終了条件 |
| 条件式の論理ミス | `&&` / `||` の優先順位、ド・モルガンの法則の誤適用 |
| 状態機械の不整合 | 状態フラグが複数箇所から書き換えられ、矛盾した状態になれるか |
| デフォルト値の意図しない使用 | ゼロ値が「未設定」と「意図的な 0」を区別できない設計になっていないか |

#### 観点 G7: HTTP クライアント・コンテキスト設定の欠陥

| チェック項目 | 確認すること |
|---|---|
| HTTP クライアントのタイムアウト未設定 | `&http.Client{}` をタイムアウトなしで使っていないか（`Timeout` フィールドを設定しているか） |
| `context.Background()` の直接使用 | 長期処理や外部通信で `context.Background()` を渡し、キャンセルできない設計になっていないか |
| リクエスト作成時の context 未設定 | `http.NewRequest` ではなく `http.NewRequestWithContext` を使っているか |

#### 観点 G8: DB・ストレージ操作の欠陥

| チェック項目 | 確認すること |
|---|---|
| ファイル読み書きの非原子性 | ファイルを直接上書きしており、書き込み中に失敗すると破損するパスがないか（tmp ファイル + rename が望ましい） |
| 競合する読み書き | 複数 goroutine が同じファイル・ストレージに対してロックなしで読み書きしていないか |
| JSON デコードのエラー無視 | `json.Unmarshal` / `json.NewDecoder(...).Decode` のエラーを捨てていないか |
| JSON エンコード後のゼロ値汚染 | `omitempty` が必要なフィールドに付いておらず、ゼロ値がシリアライズされて保存されていないか |

### 【SolidJS フロントエンド（TypeScript）】

#### 観点 F1: null / undefined アクセス

| チェック項目 | 確認すること |
|---|---|
| Optional チェーン漏れ | `obj.prop` が null / undefined になりうる場合に `?.` を使っているか |
| 非 null アサーション (`!`) の乱用 | `value!` が実際に null になりうる箇所で使われていないか |
| 配列の範囲外アクセス | `array[0]` が空配列のときにアクセスされないか |
| Wails バインディングの戻り値 | Go 側で `null` / `undefined` 相当を返しうる場合にフロントで処理しているか |

#### 観点 F2: SolidJS リアクティビティの誤用

| チェック項目 | 確認すること |
|---|---|
| シグナルの破壊的展開 | `const { value } = signal()` のように分割代入してリアクティビティを失っていないか |
| `createEffect` の依存漏れ | effect 内で使っているシグナルが正しく追跡されているか（条件分岐で隠れていないか） |
| `createEffect` 内での無限ループ | effect 内でシグナルを set しており、自己トリガーするサイクルがないか |
| `untrack` / `batch` の誤用 | 意図せず追跡を外したり、バッチ更新が期待通りに機能しているか |
| コンポーネント外でのシグナル作成 | `createSignal` / `createStore` がコンポーネントまたは `createRoot` 外で呼ばれていないか |
| `createMemo` 内での副作用 | `createMemo` はピュアな計算のみとし、シグナルの set・DOM 操作・非同期呼び出しを行っていないか |

#### 観点 F3: 非同期処理の欠陥

| チェック項目 | 確認すること |
|---|---|
| Promise のエラー処理漏れ | `.catch()` なし・`try/catch` なしの `await` がないか |
| 競合状態 (race condition) | 複数の非同期呼び出しの結果が順序保証なく状態を上書きするパスがないか |
| `createResource` のエラー状態未処理 | `resource.error` を表示・ハンドリングしているか |
| クリーンアップされない非同期処理 | コンポーネントアンマウント後に完了する非同期処理が残った状態を更新しないか |

#### 観点 F4: 型安全性の欠陥

| チェック項目 | 確認すること |
|---|---|
| `any` / `unknown` の unsafe キャスト | 型アサーション `as T` が実際の値と一致する保証があるか |
| Wails バインディング型の齟齬 | Go 側の型定義と `wailsjs/` の TypeScript 型が一致しているか |
| Union 型の網羅性 | `switch` / if-else で union 型の全ケースを処理しているか（`never` チェックがあるか） |

#### 観点 F5: メモリリーク・クリーンアップ漏れ

| チェック項目 | 確認すること |
|---|---|
| `EventsOn` のオフ登録漏れ | Wails イベントリスナーを `onCleanup` で `EventsOff` しているか |
| setInterval / setTimeout のクリア漏れ | `onCleanup` で `clearInterval` / `clearTimeout` しているか |
| 外部ストアの購読解除漏れ | `onCleanup` でサブスクリプションを解除しているか |

#### 観点 F6: ロジックバグ・境界条件

| チェック項目 | 確認すること |
|---|---|
| 空文字列と falsy 値の混同 | `if (!value)` が `""` / `0` / `false` を意図せず捕捉していないか |
| ディープコピー漏れ | オブジェクト・配列を参照のまま state に入れて意図せず共有していないか |
| インデックスベースのキー使用 | `<For>` の `key` に配列インデックスを使い、再レンダリング時にバグが起きないか |
| `<Show>` の fallback 漏れ | ローディング中・エラー時に `fallback` が指定されておらず、空白が表示されるケースがないか |

#### 観点 F7: SolidJS Props の誤用

| チェック項目 | 確認すること |
|---|---|
| `props` の直接変更 | SolidJS では props は読み取り専用。`props.value = x` のような直接変更をしていないか |
| スプレッド展開による props 転送 | `{...props}` でスプレッドするとリアクティビティが失われる。`splitProps` を使っているか |
| デフォルト値の設定方法 | `props.value ?? defaultValue` ではなく `mergeProps({ value: defaultValue }, props)` を使っているか |

## 調査手順

1. **スコープを確認** — `$ARGUMENTS` の指定に従い対象範囲を決定する
2. **型・インターフェースを把握** — `domain/` を Read して使われる型を理解する
3. **実装ファイルを読む** — Glob でファイル一覧を取得し、Read で全て読む
   - 読む順: `domain` → `application` → `infrastructure` → `adapters`（presentation）
   - 大きなパッケージは Grep で特定パターンを先に検索して絞り込む
4. **各観点でフラグを立てる** — 該当箇所が見つかったらファイル名・行番号・コード抜粋をメモする
5. **深刻度を判定** — 以下の基準で分類する
   - **高**: 実行時クラッシュ（パニック・nil 参照）、データ破損、競合状態、セキュリティ問題
   - **中**: 特定の入力で機能が正しく動かない、エラーが握りつぶされ原因追跡が困難
   - **低**: 将来バグになりうる脆弱な設計、一部のエッジケースで意図しない挙動
6. **修正案を考える** — 既存のクリーンアーキテクチャ（依存方向）を壊さない最小限の修正を提案する

## 問題の詳細

### #1 [深刻度: 高] goroutine リーク（G3）

- **該当箇所**: `internal/application/mqtt/service.go:42`
- **コード抜粋**:
  ```go
  go func() {
      for msg := range s.msgChan {
          // context キャンセルを監視していない
      }
  }()
  ```
- **問題の説明**: context がキャンセルされても goroutine が終了しない。
- **再現条件**: サービスが Close / 破棄されたあとも goroutine が残る
- **修正案**:
  ```go
  go func() {
      for {
          select {
          case <-ctx.Done():
              return
          case msg, ok := <-s.msgChan:
              if !ok { return }
              // ...
          }
      }
  }()
  ```
- **修正の影響範囲**: このファイルのみ。呼び出し元への影響なし。

## 制約事項

- **コードを読まずに記載禁止**: 実際のコードに存在しない問題を報告しない
- **該当しない観点はスキップ**: 対象スコープにない言語・機能の観点は「調査対象外」と明記する
- **修正案はアーキテクチャを壊さない**: 既存のクリーンアーキテクチャの依存方向を守った修正を提案する
- **ファイル行番号は必須**: 問題箇所は必ずファイルパスと行番号を記載する（「〜あたり」は禁止）
- **修正の影響範囲を必ず記載**: 修正が呼び出し元・共有状態・他レイヤーに与える影響を明示する
