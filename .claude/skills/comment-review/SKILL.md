このプロジェクト（Wails + Go + SolidJS）のコードコメントを下の基準で見直し、直接書き換える。変えるのはコメントだけで、コードは変えない。

指定された引数: 「$ARGUMENTS」（かぎ括弧の中が空なら引数なし）

> この Skill に書いたファイル名・関数名・コメント文は執筆時点の例である。現在のコードと食い違えば、現在のコードを正とする。

## 対象範囲

| 引数 | 範囲 |
| --- | --- |
| 無し | 未コミットの変更（`git status` と `git diff HEAD`）で追加・変更された行のコメント。変更が無ければ、受け付ける引数を示して終了する |
| `backend` | `internal/`・`tools/`・`app.go`・`main.go` |
| `frontend` | `frontend/src/`・`frontend/e2e/` |
| ファイルパス・ディレクトリパス | その配下 |

テストコード（`*_test.go`・`*.test.ts`・`*.spec.ts`）も対象に含める。

次は触らない。

- 生成物: `frontend/wailsjs/`・`frontend/src/shared/wails-events.ts`。後者のコメントを直すときは、生成元の `internal/domain/events.go` と `tools/gen-events/main.go` を直して `task go:generate:events` を実行する。
- 処理系・ツールが読む指示行: `//go:build`・`//go:embed`・`//go:generate`・`// Code generated …`・`// @vitest-environment jsdom`。
- `//nolint:…` と `// biome-ignore …` の指示部分。後ろに続く理由は見直しの対象とする（理由はコードから復元できないので消さない）。
- `internal/application/store/recovery.go` の冒頭にある復旧方針の表。AGENTS.md がここを唯一の定義として参照しているので、削らず、分量の目安も当てはめない。
- Markdown（AGENTS.md・`docs/`）と `testdata/`。

## 手順

1. 範囲内のファイルを実際に開き、コメントを 1 つずつ下の基準に当てる。コメントの真偽は、直下のコードと、コメントが名指しする関数・定数を読んで確かめる。
2. コメントの削除・書き直し・位置の移動を行う。
3. コードの変更が必要なもの（リネーム・定数化・関数の分割）は適用せず、最後の報告に候補として挙げる。
4. `git diff` で、コメント以外の行が変わっていないことを確かめる。
5. `task format` と `task lint` を実行する（公開シンボルの doc コメントは revive の `exported` が検査する）。

最後に、会話上で次を報告する（レポートファイルは作らない）。

- 消した・書き直したコメントの件数と、代表的な例
- コードと食い違っていたコメント（`ファイル:行` と、どう食い違っていたか）
- 手順 3 の候補（`ファイル:行` と、直す内容）

## 1. 何を書くか — コードから復元できないことだけ

判断基準は 1 つ。「このコメントを消したら、読む人は何を失うか」。失うものが無ければ消す。書いてよいのは、コードを読んでも復元できない情報である。

- なぜこの値・この順序なのか（例:「64bit 整数は number 入力だと桁が落ちるため、専用の種別に分けている。」）
- 何を変えると何が壊れるか（前提条件・不変条件。例:「stateMu 保持中に呼ぶ」「done を閉じた後にだけ読む」）
- 外部ライブラリ・処理系・プロトコルの非自明な仕様、直感に反する挙動（例:「同じクライアント ID で接続すると、ブローカーが元の接続を切る。」。Wails・paho・SolidJS のリアクティビティ・Windows のファイル操作も同じ）
- workaround を入れた理由と、それが不要になる条件
- 過去の不具合から入れたガード（再発すると被害が出るもの。例:「プロファイルが空のまま restore() すると、保存値を消してしまう」）
- 握りつぶしているエラーの理由（`//nolint:errcheck` の後ろなど）
- 従っている決定への参照（AGENTS.md の節、`docs/` の設計文書）

## 2. 何を書かないか

| 書かないもの | 例 | どこにあるべきか |
| --- | --- | --- |
| コードの実況（WHAT） | `// プロファイルを取得する` の下に `p, err := repo.Get(id)` | コード自身 |
| 型・シグネチャのなぞり書き | 「id は string である」「エラーを返す」 | シグネチャ |
| 作業経緯・変更履歴 | 「service.go から移設した」「旧実装では〜だった」「後続で整備する」 | Git 履歴 |
| issue / PR 番号 | `#312` | Git 履歴 |
| 当たり前のこと | 「公開メソッドしか呼べない」 | — |
| やらないことの列挙 | 「〜はここに宣言しない」「〜は持たない」 | 意図的に外したなら AGENTS.md・`docs/` |
| 呼び出し元 | 「呼ぶのは `MQTTHandler.Connect`」「`app.go` から呼ばれる」 | —（呼び出し側が守る前提は不変条件なので書いてよい） |
| 別の実装の説明 | interface のコメントに「paho の実装では〜」 | その実装の型 |
| 1 つの実装しか満たさないことを、ポートの不変条件として書く | `domain` のポートに「保存は一時ファイル経由で行う」 | その実装（`infrastructure`） |
| 層の規約の繰り返し | 「application は infrastructure を import しない」 | AGENTS.md |
| 設計の弁護 | 「なぜこの実装が良いか」「素朴にやると何が起きるか」 | コミットメッセージ・`docs/` |
| コメントアウトしたコード | `// client.Disconnect(250)` | Git 履歴（消す） |

「素朴にやると何が起きるか」でも、次に変更する人がその書き方へ戻しかねないものは「何を変えると何が壊れるか」にあたるので残す。

## 3. コメントより先に直すもの

ここに当たるものはコードの変更になるので、適用せずに候補として報告する。

- 名前で説明できるならリネームする。「`mode` とは何か」を書きたくなったら、名前を直す。裸の `-1` に意味があるなら、名前付き定数にする。名前を直せないときだけコメントにする。
- 値ではなく定数名を引く。`scanQuiesce` の横に「250 ms」と書くと、定数を変えた瞬間に嘘になる。`scanQuiesce` と書く。
- 長い説明が要るなら、関数を分ける。説明したい塊は、たいてい名前を付けられる。
- Go・TS の区切りコメント（`// --- Hooks ---`）が要るファイルは、分割の候補である。CSS のセクション見出し（`/* ── Send form ── */`）は残してよい。テスト・spec のセクション見出し（`// --- GetRootItems ---`・`// ── 観点A: 空状態 ──`）も同じく残し、候補として報告しない。

## 4. 形式 — STE（Simplified Technical English）

読み手の速度を落とさないための、機械的な形式規則である。

- コメントは日本語で書く（AGENTS.md）。英語のコメントは、残すと決めたものだけ日本語に書き直す。`//nolint`・`biome-ignore` の理由も同じ。識別子・イベント名・プロトコル用語（`retained`・`SUBACK`）は訳さない。
- 1 文は 40 字前後で切る。長い文は 2 文に割る。
- 1 文に動作を 2 つ入れない。「A して B する」は 2 文にする。
- 結論を最初の 1 文に置く。前置き・例外・やらない理由を先に並べない。
- 1 コメント 1 話題。話題が変わるなら、コメントを分けるか、そこで切る。
- 同じものを複数の言い方で呼ばない。コードと UI の用語に合わせる（プロファイルを「接続設定」「接続情報」と呼び替えない）。
- 比喩・曖昧な修飾を使わない。「〜のようなもの」「事実上の」「いわば」は削る。
- 文中の強調（`**…**`）を使わない。一番大事なことを最初の文に書けば足りる。
- バッククォートはコード上の名前にだけ使う。Go の doc コメントでは使わず、識別子をそのまま書く（既存のコードに合わせる）。
- 括弧で囲む。読点で挟まない。「A（B のとき）は C する」。読点で挟むと、どこで閉じたのかが読み取れない。全角・半角はそのファイルの既存の書き方に合わせ、付け替えだけの変更はしない。

## 5. 分量と置き場所

- コメントは 3 行以内。それを超える塊は、ファイル 500 行あたり 1 つまでを目安にする。不変条件・前提条件（どのロックがどのフィールドを守るか、取得の順序、所有権の境界）と、戻り値の場合分けは目安を超えてよい。同じ不変条件は 1 か所にまとめる。
- コメントは直下のコードを説明する。`if` の上のコメントは、その分岐の説明として読まれる。逆の場合を説明したいなら `else` 側に書く。位置の誤りはスタイルではなくバグである。
- 日本語のコメントは文として書き、句点で終える。行末に付ける短い付記（`_ = conn.Close() //nolint:errcheck // 後始末。閉じる失敗は無視してよい` の理由を含む）は句点を付けなくてよい。
- 一時的なメモは `TODO:` を付け、コミット前に消す。残すなら、何が未解決かを書く。

### doc コメント（Go の宣言の直前、TS の `/** … */`）

doc コメントは宣言の続きであり、宣言の言い換えではない。

- Go の公開シンボルは識別子名で始める（`LoadSingleFile は repo.Load の結果を policy に従って解釈する。`）。revive の `exported` が検査する。非公開のものも同じ形にそろえる。
- 関数・メソッド・型は「何をするか」を述語で書く。
- フィールド・定数・TS のプロパティは名詞句でよい（`/** 同時に保持する最大件数。超過時は最古を落とす。 */`）。
- シグネチャをなぞらない。引数について書くのは、型から読み取れないこと（単位・符号の意味・境界値・nil を許すか）だけにする（「logger は nil を許容し、その場合ログ出力をスキップする。」「自動消滅までの時間 (ms)。0 以下で自動消滅しない。」）。
- 引数ではなく結果を書く。呼び出し側に見えているのは渡した引数なので、書く価値があるのは「渡すと何が起きるか」である。戻り値は型ではなく、返る値が何を表すかを書く（「読めない URL は null。」）。
- TS では `@param`・`@returns` を使わず、本文に書く（既存のコードに合わせる）。`/** … */` と `//` はそのファイルの既存の使い分けに合わせ、記法の付け替えだけの変更はしない。
- ポート（Go の interface、TS の `XxxApi`・`domain/<proto>/ports.ts`）のコメントには、すべての実装が守る契約だけを書く。
- ドメイン型の json タグ、`storedXxx` DTO のフィールドに「RPC 用」「保存用」と書かない。置き場所が示している。
- 独立した段落として読める doc コメントは、たいてい設計の弁護が紛れている。

### テストコード

- テスト名で言えることはコメントにしない（`TestLoadSingleFile_CorruptIsQuarantined`、`it("…")` の文字列）。
- 書くのは、その入力値・その待ち方を選んだ理由（例: 境界値である理由、`time.Sleep` を使わざるをえない理由）。
- `// Arrange`・`// Act`・`// Assert` のような区切りは消す。テストをまとめるセクション見出しは残す（3 節）。

## 6. 迷ったときの手順

1. 消してみる。読む人が何も失わないなら、そのまま消す。
2. 失うものがあるなら、それが「コードから復元できない情報」か確かめる。違うなら、名前・構造で直す（候補として報告する）。
3. 残すと決めたら、40 字前後の文に割り、結論を先に置く。
